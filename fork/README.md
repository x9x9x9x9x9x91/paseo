# The fork's release line

This fork ships Paseo's desktop app with features upstream has not merged yet. `fork/release` is upstream's latest stable tag plus the fork's own commits, and every upstream stable release gets a fork release the same day. Today that is:

- the Quote button: select text in an agent message and quote it into the composer, upstream pull [#7176](https://github.com/getpaseo/paseo/pull/7176);
- a daemon patch: a chat on a custom provider (the zero-retention Claude) has its workspace named, and its checkout's commit and pull request text written, on that provider only. Upstream names on the first provider with a Haiku, whatever provider the chat runs on, so a private chat's first message reached the subscription. Its pull, [#7313](https://github.com/getpaseo/paseo/pull/7313), was closed for upstream's [#7611](https://github.com/getpaseo/paseo/pull/7611), which makes Settings > Host > Metadata > Manual use only the chosen model; so the patch is `Upstream: none` and `Superseded-by: getpaseo/paseo#7611`, and leaves the fork with the first stable release that carries #7611 (Superseded features, below). The patch reaches a running daemon only when that daemon runs from the app: a daemon under Alma's `com.alma.paseo-daemon` runs Homebrew's stock `@getpaseo/cli`;
- the projects choice in Settings > Notifications: count every project toward the Dock badge and the OS banners, or only the chosen ones. It has no upstream pull (`Upstream: none`), so it holds the retirement while it is on the branch.

## What a fork release changes

The app (`packages/app`), the build config (the update feed in `packages/desktop/electron-builder.yml`, this folder, and the packaged-app smoke's deadline in `packages/desktop/e2e/packaged-app-smoke.js`, raised from upstream's 60 s to 240 s because the build Mac is shared and a loaded one cold-starts the daemon past a minute), and the daemon patch's files, listed with their tests in `DAEMON_PATCH_FILES` and `DAEMON_PATCH_TESTS` in `release.mjs`. The rest of the daemon, the CLI, the desktop shell and the lockfile are upstream's source of the same tag; the job refuses to build a branch that changes anything else. Swapping the app leaves a running daemon alone: the desktop app stops only a daemon it started itself, so the daemon patch takes effect at the daemon's next restart. The daemon patch is written on the fork's stable base; its upstream pull's branch, `custom-provider-naming`, is the same change on upstream's main, so when the rebase onto the next stable tag stops in its files (`create-agent/create.ts`, `tools/paseo-tools.ts`, `schedule/service.ts`, and the create test's call, which gains upstream's third argument), resolve the conflict by taking that branch's version of the file.

Commits that belong to the fork itself (the feed, this job) start with `fork: `. Every other commit is a feature, and its upstream pull goes in `UPSTREAM_PULLS` in `release.mjs`. A feature with no upstream pull carries the trailer `Upstream: none` in its message.

### Superseded features

A feature upstream replaces with a change of its own, rather than by merging the fork's pull, carries the trailer `Superseded-by: getpaseo/paseo#<pull>` (more than one, comma-separated, when it takes several). The rebase onto the first stable release that carries every pull it names leaves the commit out (a branch already on that release is replayed in place without it), and Tim gets one notice naming it, with the commit message's own words on what takes its place (the daemon patch says which setting to pick), so its message says that before its trailers. A superseded feature that is also `Upstream: none` stops holding the retirement in that same rebase. Once the daemon patch has left, the daemon's files are upstream's again and its tests leave the gate with it.

## Versions

A fork release is the upstream version plus `-fork.N`: `0.11.4-fork.1`, then `0.11.4-fork.2` when a commit lands on `fork/release` before upstream's next release, then `0.11.5-fork.1`. The tag and the GitHub release carry the same name, without a `v`, so upstream's release workflows (triggered by `v*` tags) never match it.

Semver reads `0.11.4-fork.1` newer than every older upstream release and every earlier fork build, so the app updates; the app keeps the stock `latest` channel. The renderer reads its version from `packages/app`, which stays upstream's, so the app/daemon version check compares `0.11.4` with the daemon's `0.11.4`.

## Signing

Electron's updater on macOS installs a build only when it satisfies the running app's designated requirement, which by default names the one team that signed the app: a stock app (signed by upstream's team, `99ZMJMKU9Y`) never takes a fork build. The job signs through `sign-mac.cjs`, which gives the fork app a designated requirement naming Paseo's identifier `sh.paseo.desktop` and either team, the fork's `HKM8HFGKC6` or upstream's, so a fork app could take stock Paseo; the helpers inside keep their own requirements. What it takes is still only what its feed offers, and the fork's feed offers fork builds until the handover below. Pinned to the identifier, the requirement admits no other app from either team. The job's verify step refuses a build whose requirement is not this one, and codesign refuses one that does not satisfy its own.

## The job

`release.mjs` runs hourly on sincoder as the launch agent `com.alma.paseo-fork-release`, inside the logged-in session, because the Developer ID key and the `substrate-notary` profile live in its login keychain, which is locked over ssh. sincoder is the main Mac, where nothing builds: the checks, the build and the packaged-app smoke run on a test Mac over ssh, and sincoder keeps what needs its keys and logins, git and GitHub, the conflict agent, signing, notarizing and publishing. `install.sh` sets it up under `~/Coding/_forks/paseo-release` on sincoder: `tools/` follows `fork/release` and holds the job, `build/` is where it rebases (git only, no `node_modules`), `signer/` holds the `@electron/osx-sign` the build used. Each run with something to do leaves its logs in `runs/<time>/`, the build host's included; `state.json` and `job.log` say what it last did.

The build host is the first of `PASEO_FORK_BUILD_HOSTS` (default `mini1 mini2 mini3`) that answers over ssh with Night's `~/.local/bin/ns-with-max-lock` installed; each half of the build runs under that Mac's Max lock as `guest:paseo-fork-release`, so a Night Max leg never runs beside it. The job sets the host up itself: `~/Coding/_forks/paseo-release` there gets a bare start of a clone (sincoder pushes the candidate to its `fork-candidate` branch with upstream's tag), this job's two files in `tools/fork/` each run, the run folder, and the Node major upstream's workflow names (`brew install node@N` when missing). No key, login or GitHub access is needed there.

A run asks GitHub for upstream's latest release (published, not a prerelease), then:

1. A newer upstream release: rebase the branch onto its tag, leaving out the superseded features the tag replaces. On a conflict, a headless agent tries once; it reaches sincoder's own model proxy (`PASEO_FORK_PROXY_URL`, default `http://127.0.0.1:8318`), since sincoder has no login of its own. If it cannot resolve the conflict, Tim gets a notice with the conflict and the app stays on the last release.
2. On the build host, under its Max lock: check, on the Node major upstream's release workflow uses: typecheck, lint, format, this folder's tests, the app's unit tests, the daemon patch's tests while the branch carries it, and the features' Playwright specs (every browser spec the branch adds or changes on upstream's tag, read from the branch, so a new feature's spec runs with nothing to list; a feature is gated by the spec it adds or changes, and a branch that changes the app with none fails the run). Then build the arm64 app unsigned: electron-builder hands it to `sign-mac.cjs`, which writes a signing plan (every path's options and what to leave unsigned, as electron-builder gives them) instead of signing.
3. On sincoder: sign the app from that plan with the same `@electron/osx-sign` version, as `Developer ID Application: Tim Roth (HKM8HFGKC6)`, notarize and staple it, and verify the signature, the designated requirement, the notarization, the version and the feed inside the app.
4. On the build host again: the signed app passes the packaged-app smoke and is packed into the zip, the dmg, their blockmaps and `latest-mac.yml` without being touched (`--prepackaged`). Back on sincoder, the app inside the zip, the one the updater installs, is verified once more.
5. Push the rebased branch and publish the release, with `latest-mac.yml`, the zip and dmg and their blockmaps, marked latest.

It publishes only when every step passed. A failure keeps the previous release and goes to Tim's notifications on sincoder through Alma's door, as source `paseo-fork`; the same upstream release and branch are retried for three runs, then the job waits for a new upstream release or a new commit. A build host that does not answer, or one whose Max lock stays held past its wait, is no failure of the release: nothing is counted and the next hour tries again. Every state write is copied to `~/Vault/Alma/Local/Task-State/paseo-fork/state.json`, where Alma's sched_watch warns when the job has not checked upstream for 12 hours. A run whose build host was away writes no state, so a job stopped, sincoder down or no build host for half a day all reach Tim that way.

Run it by hand on sincoder through `~/bin/gui-run.sh` so it gets the session's keychain. `--dry-run` builds, signs, notarizes and verifies without pushing, publishing or notifying, and keeps the release files in its run folder; `--branch <name>` builds another branch of the fork, `--force` builds a branch that is already released and `--retire` builds the handover below from upstream's latest release, all three with `--dry-run` only.

## Retirement

When upstream merges the features, the fork hands the app back and stops. A run retires when every pull in `UPSTREAM_PULLS` is merged into the new stable release, or when the rebase drops every feature commit as already upstream. A feature marked `Upstream: none` holds the retirement: the handover would drop it. With one on the branch, a release that carries every listed pull fails with a notice instead; take the merged features' commits off `fork/release` and their pulls out of `UPSTREAM_PULLS`, and the next run rebases the rest. With only such features left, the fork stays until they leave the branch: dropped by a rebase once upstream carries them, or taken off by hand. It then builds upstream's tag as it is, with upstream's update feed, signs it as above, numbers it like any fork release (`0.12.0-fork.1` on upstream `v0.12.0`) and publishes it as the fork's last release, its tag on upstream's commit. A fork app takes it because the fork signed it; that build then finds stock `0.12.0` on upstream's releases, newer than `0.12.0-fork.1`, and takes it because its requirement names upstream's team. Two updates, no hand install, and the daemon and its agents keep running. The job renames its launch agent so it does not load again and tells Tim; a failed handover is retried like any release. A pull upstream closes without merging never lands. The next run tells Tim, once per pull, and goes on releasing as before: give the feature's commit the trailer `Upstream: none` (in place of the pull's number when it carries that) and take the pull out of `UPSTREAM_PULLS`, or, when upstream carries the change in a pull of its own, put that pull in `UPSTREAM_PULLS` in its place.
