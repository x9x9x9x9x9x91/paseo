# The fork's release line

This fork ships Paseo's desktop app with features upstream has not merged yet. `fork/release` is upstream's latest stable tag plus the fork's own commits, and every upstream stable release gets a fork release the same day. Today that is:

- the Quote button: select text in an agent message and quote it into the composer, upstream pull [#7176](https://github.com/getpaseo/paseo/pull/7176);
- the projects choice in Settings > Notifications: count every project toward the Dock badge and the OS banners, or only the chosen ones. It has no upstream pull (`Upstream: none`), so it holds the retirement while it is on the branch.

The daemon patch, which kept a custom provider's chat naming and commit text on that provider ([#7313](https://github.com/getpaseo/paseo/pull/7313)), left with upstream's [#7611](https://github.com/getpaseo/paseo/pull/7611), in every stable release since v0.13.0: Settings > Host > Metadata > Manual uses only the chosen model. The fork changes no daemon file since.

## What a fork release changes

The app (`packages/app`), the build config (the update feed in `packages/desktop/electron-builder.yml`, this folder, and the packaged-app smoke's deadline in `packages/desktop/e2e/packaged-app-smoke.js`, raised from upstream's 60 s to 240 s because the build Mac is shared and a loaded one cold-starts the daemon past a minute). The daemon, the CLI, the desktop shell and the lockfile are upstream's source of the same tag; the job refuses to build a branch that changes anything else (`checkScope`), so a lane runs that check in its tree before every push to `fork/release`, its own fix's or any other (ALM-5061): `git fetch https://github.com/getpaseo/paseo.git refs/tags/<tag>:refs/tags/<tag>`, then `node --input-type=module -e 'const {checkScope} = await import("./fork/release.mjs"); checkScope("<tag>", {cwd: process.cwd()})'`, `<tag>` upstream's tag the branch is on. Swapping the app leaves a running daemon alone: the desktop app stops only a daemon it started itself.

Commits that belong to the fork itself (the feed, this job) start with `fork: `. Every other commit is a feature, and its upstream pull goes in `UPSTREAM_PULLS` in `release.mjs`. A feature with no upstream pull carries the trailer `Upstream: none` in its message.

### Superseded features

A feature upstream replaces with a change of its own, rather than by merging the fork's pull, carries the trailer `Superseded-by: getpaseo/paseo#<pull>` (more than one, comma-separated, when it takes several). The rebase onto the first stable release that carries every pull it names leaves the commit out (a branch already on that release is replayed in place without it), and Tim gets one notice naming it, with the commit message's own words on what takes its place, so its message says that before its trailers. A superseded feature that is also `Upstream: none` stops holding the retirement in that same rebase.

## Versions

A fork release is the upstream version plus `-fork.N`: `0.11.4-fork.1`, then `0.11.4-fork.2` when a commit that changes the app lands on `fork/release` before upstream's next release, then `0.11.5-fork.1`. The tag and the GitHub release carry the same name, without a `v`, so upstream's release workflows (triggered by `v*` tags) never match it.

Semver reads `0.11.4-fork.1` newer than every older upstream release and every earlier fork build, so the app updates; the app keeps the stock `latest` channel. The renderer reads its version from `packages/app`, which stays upstream's, so the app/daemon version check compares `0.11.4` with the daemon's `0.11.4`.

## Signing

Electron's updater on macOS installs a build only when it satisfies the running app's designated requirement, which by default names the one team that signed the app: a stock app (signed by upstream's team, `99ZMJMKU9Y`) never takes a fork build. The job signs through `sign-mac.cjs`, which gives the fork app a designated requirement naming Paseo's identifier `sh.paseo.desktop` and either team, the fork's `HKM8HFGKC6` or upstream's, so a fork app could take stock Paseo; the helpers inside keep their own requirements. What it takes is still only what its feed offers, and the fork's feed offers fork builds until the handover below. Pinned to the identifier, the requirement admits no other app from either team. The job's verify step refuses a build whose requirement is not this one, and codesign refuses one that does not satisfy its own.

## The job

`release.mjs` runs hourly as `com.alma.paseo-fork-release` on the signing Mac, mini1, as its agent account's timed job (the factory's `scripts/agent-host/paseo-fork-release.sh`), which holds no key: `PASEO_FORK_RELEASE_PROGRAM` names the release account's program (Alma's ALM-4593), whose `notary-check` asks the notary before the build and whose `sign` takes the unsigned app with its plan in one zip and hands it back signed, notarized and stapled, which the job then verifies as its own (`signThere`, ALM-4279); with `PASEO_FORK_RELEASE_PROGRAM` unset, the job signs with the running account's own login keychain, which then holds the Developer ID key and the `substrate-notary` profile. The plan carries the bundle's two-team requirement itself, as that program adds none. Its notices name the run folder's Mac as `HERE`, `alma@mini1`. Nothing builds on the signing Mac: the checks, the build and the packaged-app smoke run on a test Mac over ssh, and the signing Mac keeps what needs its keys and logins, git and GitHub, the conflict agent, signing, notarizing and publishing. `install.sh --clones-only` sets it up under `~/Coding/_forks/paseo-release` on mini1, whose job the factory's `agent_jobs.py` installs; on another signing Mac a plain `install.sh` sets up the same clones and installs the job as that account's launch agent, from `com.alma.paseo-fork-release.plist` here. On either path, `tools/` follows `fork/release` and holds the job, `build/` is where it rebases (git only, no `node_modules`), `signer/` holds the `@electron/osx-sign` the build used. Each run with something to do leaves its logs in `runs/<time>/`, the build host's included; `state.json` and `job.log` say what it last did. Every failed run's notice, whatever step failed and a conflict the agent could not resolve included, comes to Alma's Notifications as an agent's ask naming `job.log` and `runs/`, the body naming the run's own folder: Alma's night run reads it by this README and files a fix in the fork as a row a lane builds on `fork/release`. What only Tim can do, a login, a key, the notary profile, a test Mac that stays away, or taking a retired feature's commits off the published branch, it hands back to him. The other notices (a conflict resolved, a feature superseded, a retirement, a pull closed upstream) are notes for Tim.

The build host is the first of `PASEO_FORK_BUILD_HOSTS` (default `mini2 mini3`; never mini1, the machine room where nothing builds, ALM-4328) that answers over ssh with Night's `~/.local/bin/ns-with-max-lock` installed; each half of the build runs under that Mac's Max lock as `guest:paseo-fork-release`, so a Night Max leg never runs beside it. The job sets the host up itself: `~/Coding/_forks/paseo-release` there gets a bare start of a clone (the signing Mac pushes the candidate to its `fork-candidate` branch with upstream's tag), this job's two files in `tools/fork/` each run, the run folder, and the Node major upstream's workflow names (`brew install node@N` when missing). No key, login or GitHub access is needed there.

A run asks GitHub for upstream's latest release (published, not a prerelease), then:

1. A newer upstream release: rebase the branch onto its tag, leaving out the superseded features the tag replaces. On a conflict, a headless agent tries once; it reaches the signing Mac's own model proxy (`PASEO_FORK_PROXY_URL`, default `http://127.0.0.1:8318`), since the job has no login of its own. If it cannot finish the rebase, Tim gets a notice with the conflict, which of the three attempts it was and where the next run starts, and the app stays on the last release. The build clone keeps the rebase, whole or up to the stop the agent could not get past, and the next run replays only the commits after it, so a failed try keeps its port and a new commit is ported alone; a fork commit amended below it, or `build/.git/fork-kept-rebase.json` removed, starts a fresh port (`rebaseOnto`, ALM-4637).
2. On the build host, under its Max lock, in a checkout of the candidate with the last build's git-ignored files cleared, as upstream's CI starts (`checkoutCandidate`, ALM-4548): check, on the Node major upstream's release workflow uses: typecheck, lint, format, this folder's tests, the app's unit tests (a failed test tried once more, `--retry=1`, so one upstream timing flake does not fail a run while a test that fails twice still does, and each test that passed only on its retry named in the build host's log, ALM-4585), and the features' Playwright specs (every browser spec the branch adds or changes on upstream's tag, read from the branch, so a new feature's spec runs with nothing to list; a feature is gated by the spec it adds or changes, and a branch that changes the app with none fails the run). Then build the arm64 app unsigned: electron-builder hands it to `sign-mac.cjs`, which writes a signing plan (every path's options and what to leave unsigned, as electron-builder gives them) instead of signing.
3. On the signing Mac: sign the app from that plan with the same `@electron/osx-sign` version, as `Developer ID Application: Tim Roth (HKM8HFGKC6)`, notarize and staple it, and verify the signature, the designated requirement, the notarization, the version and the feed inside the app.
4. On the build host again: the signed app passes the packaged-app smoke and is packed into the zip, the dmg, their blockmaps and `latest-mac.yml` without being touched (`--prepackaged`). Back on the signing Mac, the app inside the zip, the one the updater installs, is verified once more.
5. Push the rebased branch and publish the release, with `latest-mac.yml`, the zip and dmg and their blockmaps, marked latest.

A head that changes only the job's own files since the published release ships that release's app, so it runs step 2 only and signs, notarizes and publishes nothing: the job's tools, `tools/`, follow the branch at once, and Tim's app gets no update that changes nothing. The job's files are this README, `release.mjs`, `release.test.mjs`, `install.sh` and `com.alma.paseo-fork-release.plist`, the launch agent a plain `install.sh` installs, and of `release.mjs` only the parts `TOOLS_PARTS` lists (deciding, polling, rebasing, the gate's checks, the build host's plumbing, state and notices); `sign-mac.cjs`, any other file, and every other part of `release.mjs` change the app, so a new part changes it until it is listed, in the commit that adds it. A head the gate passed is not run again (`onlyToolsChanged`, `state.json`'s `gated`, ALM-4638).

A run with work to do waits while Ableton Live is open on the signing Mac (`pgrep -x Live`): the main's music comes first, and signing, notarizing and the conflict agent run there. Nothing is counted; the same candidate is tried the next hour. It publishes only when every step passed. A failure keeps the previous release and goes to Tim's notifications through Alma's door on the signing Mac, as source `paseo-fork`; the same upstream release and branch are retried for three runs, then the job waits for a new upstream release or a new commit. Each upstream release has one note, which every failed run rewrites with its own step and run folder, never a note per attempt; a newer upstream release settles an older one's note, and the run that publishes or retires rewrites the notes still open as reports that need nobody. A failure's note is an agent's ask, which Alma's night run (agent-asks) takes by this README: it reads the run folder the note names and `job.log`, finds the cause, and names the fix in its outcome's row, which Alma files as a To-Do row a lane builds. The lane commits the fix to `fork/release` from a clone of the fork, never the job's own checkout, which every run forces back, once the scope check above passes in its tree and the build host's whole `app` half (`hostPhase`) passes on a test Mac, not only the step that failed, so one lane finds every failure of the candidate (ALM-4661): `PREPARE_STEPS`, every `gateSteps` check with the specs `branchSpecs` names, and `buildApp`'s unsigned build. Its push is the routine release line and the re-run: a new commit is a new candidate, and the lane starts that run itself rather than wait for the hourly one, with `python3 ~/Coding/factory/scripts/agent-host/agent_jobs.py kick com.alma.paseo-fork-release` on mini1, which starts the job where it runs. A failure at a step that talks to GitHub or Apple's notary (`OUTSIDE_STEPS`: `github`, `push`, `publish`, `notarize`) is most often no bug of the branch and needs no fix: it is not counted toward the three runs until a day has passed since the first of the failed runs running at those steps, so the job runs it again every hour until GitHub or the notary is back, and a fault that lasts (a token that may not upload a release) still stops the hourly rebuilds after that day and three more runs. Apple's answer that the app is Invalid is the signing's fault and counts at once. Apple refusing the `substrate-notary` profile (HTTP 401, a password Apple no longer takes, or 403, most often a developer agreement to accept) is no outage but Tim's step, so a run that is to build asks the notary first (`notarytool history`, about a second), before the build host: while it refuses, nothing is built or counted, the release's note becomes that step once per candidate, an ask that needs Tim and no agent, and each hour asks again until the first one let in builds and publishes (ALM-4009); a refusal at notarize itself counts at once. A build host that does not answer, or one whose Max lock stays held past its wait, is no failure of the release: nothing is counted and the next hour tries again. Every state write is copied to `~/Vault/Alma/Local/Task-State/paseo-fork/state.json`, where Alma's morning brief warns in its Paseo fork line when the job has not checked upstream for 12 hours (`paseo_fork_signals`, ALM-3645). A run whose build host was away writes no state, so a job stopped or no build host for half a day both reach Tim that way.

Run it by hand on mini1 as its agent account through the factory's `scripts/agent-host/paseo-fork-release.sh`, which sets `PASEO_FORK_RELEASE_PROGRAM`. `--dry-run` builds, signs, notarizes and verifies without pushing, publishing or notifying (a head that changes only the job's files runs the gate only, as above, unless `--force` is given too), and keeps the release files in its run folder until the next dry run ends (`pruneRuns`, ALM-5078); `--branch <name>` builds another branch of the fork, `--force` builds a branch that is already released and `--retire` builds the handover below from upstream's latest release, all three with `--dry-run` only.

## Retirement

When upstream merges the features, the fork hands the app back and stops. A run retires when every pull in `UPSTREAM_PULLS` is merged into the new stable release, or when the rebase drops every feature commit as already upstream. A feature marked `Upstream: none` holds the retirement: the handover would drop it. With one on the branch, a release that carries every listed pull fails with a notice instead; take the merged features' commits off `fork/release` and their pulls out of `UPSTREAM_PULLS`, and the next run rebases the rest. With only such features left, the fork stays until they leave the branch: dropped by a rebase once upstream carries them, or taken off by hand. It then builds upstream's tag as it is, with upstream's update feed, signs it as above, numbers it like any fork release (`0.12.0-fork.1` on upstream `v0.12.0`) and publishes it as the fork's last release, its tag on upstream's commit. A fork app takes it because the fork signed it; that build then finds stock `0.12.0` on upstream's releases, newer than `0.12.0-fork.1`, and takes it because its requirement names upstream's team. Two updates, no hand install, and the daemon and its agents keep running. The job tells Tim and does nothing more from then on (`state.json`'s `retired`); a launch agent from a plain `install.sh` it renames so it does not load again, and mini1's job, which its own run cannot stop, the factory's `agent_jobs.py sync` removes at the next landing's refresh once `state.json` says `retired` and its last notice went out (`retired_on`, Alma's ALM-5050); a failed handover is retried like any release. A pull upstream closes without merging never lands. The next run tells Tim, once per pull, and goes on releasing as before: give the feature's commit the trailer `Upstream: none` (in place of the pull's number when it carries that) and take the pull out of `UPSTREAM_PULLS`, or, when upstream carries the change in a pull of its own, put that pull in `UPSTREAM_PULLS` in its place.
